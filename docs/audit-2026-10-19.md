# Kaitou Audit: 19 October 2026 (MYT)

## Scope and limits

This is a broad application audit, not a penetration-test certificate or a guarantee that no defects remain. No new paid order, supplier purchase, bank payment, live refund, staff creation, price edit or funding deposit was performed. Existing seller prices/publication choices were preserved. Financial behaviour changes listed below require a separate approved implementation.

Buyer coverage: home, About, Order Status, Rankings and all four current game pages; 390px and 1440px widths; light and dark themes (32 screenshot/DOM cases). All returned HTTP200 with no detected page-wide horizontal overflow or uncaught browser exceptions in this pass. The first screenshot harness runs needed selector fixes; those harness errors are not application failures. A simulated failed checkout then revealed the real form-reset issue below.

Admin visual coverage: Overview, Products, Orders, Failed review, Revenue, Staff, Integrations and Settings using the owner's existing normal Chrome login. Destructive and paid controls were not clicked. Automated visitor/API tests run without credentials. A proposed synthetic privileged session was rejected by the safety reviewer and removed; no session bypass was used. Admin mobile CRUD, keyboard-only traversal of every admin control, assistive-technology testing, load testing and independent security penetration testing remain outside the verified scope.

Screenshots/JSON are in the ignored local artifacts/audit-2026-10-19-after directory; they are excluded from Git and future Vercel uploads. Simulated checkout screenshots are explicitly labelled and do not represent real orders.

## Fixed in this audit

1. **High: direct supplier-cost exposure through Supabase.** Anonymous-role SQL could read 73 active variation cost rows and four supplier product mappings, even though the website projection hid them. Catalogue reads are server-side, so unnecessary anon/authenticated table privileges were revoked. Verified anonymous/authenticated column access is now false and service_role access remains true. No claim is made that someone actually accessed this information.
2. **Medium: light-theme checkout contrast.** The light-theme white-text override recoloured the dark price badge and payment button. Explicit dark-surface boundaries now preserve white text; computed colours were verified on mobile/desktop in both themes.
3. **Medium: link colour override.** An unlayered global anchor colour rule overrode utility text colours, including the green payment continuation link. Removed that override, retaining Tailwind's normal base inheritance.
4. **Medium: missing game posters.** The provider returned artwork but product queries/imports dropped it. Existing image_url schema is now used throughout reads, imports, create/edit and buyer rendering. Verified supplier artwork saved for all four current products; HTTPS validation and an image-error fallback are present. No prices or active flags were changed.
5. **Medium: failed checkout cleared entered details.** React form-action success resolution reset uncontrolled fields even after a handled API error. Checkout and Order Status now prevent native reset and retain values for retry. Error feedback has an alert role. Final simulated retry verification is recorded in the browser report.
6. **Medium: missing basic response hardening.** Added anti-framing, MIME-sniff prevention and referrer-policy headers. A nonce-based Content Security Policy is not included and remains a separate hardening item.
7. **Medium: database function hardening.** Fixed mutable search_path for set_updated_at and revoked public execution of the automatic-RLS event-trigger function. The follow-up security advisor no longer reports either warning.
8. **Low: completed orders labelled as queued.** The all-paid Orders page called every order 'in queue', including completed launch tests. Changed its count label to 'paid orders'; failed-review counts retain queue wording.

## Open findings, ordered by priority

### R1: High - manual-rate profit still depends on the funding ledger

Evidence: docs/atomic-funding-allocation.sql checks v_available against cost_usd before allocating any order, including one with cost_exchange_rate. The admin visual check confirmed live supplier credit and recorded ledger credit differ following a replenishment. No customer orders currently exist, so this is a prospective reporting failure, not a claim of lost paid orders.

Impact: a successfully delivered order can remain outside reported allocated profit until the owner manually reconciles funding. This undermines the simplified one-rate costing model.

Recommendation: separate confirmed supplier cost/profit recognition from deposit bookkeeping for new manual-rate orders. Keep historical allocations immutable and keep live supplier reservations as the stock control. Do not invent missing funding deposits.

### R2: High - refunded-order losses disappear from the profit report

Evidence: src/lib/revenue.ts:6 includes only processing/completed/review, and the report query at line149 excludes refunded status entirely. Supplier cost may still be consumed when a customer is refunded.

Impact: the dashboard can omit an unrecovered supplier debit and payment fee rather than reporting the loss. This is a code-path finding; no live refund was performed.

Recommendation: model customer refunds, supplier refunds and non-refundable gateway fees separately; include losses and reversals in the report. Customer refund recording must never imply that FazerCards returned credit.

### R3: Medium - later cost confirmation has no automatic allocation retry

Evidence: src/lib/fulfillment-sync.ts updates a newly confirmed supplier debit but does not call the allocator. src/app/api/cron/fulfillment/route.ts runs expiry/recovery/polling, not a pending-profit reconciliation pass. Initial allocation failures can also remain pending until the admin uses Allocate pending paid orders.

Recommendation: add a bounded, idempotent cost-recognition reconciliation step after supplier confirmation, designed together with R1.

### R4: Medium - Revenue actions can stay busy after a network error

Evidence: src/components/admin-revenue-dashboard.tsx loadRevenue/onCreateFundingBatch/allocateFunding set busy flags before await fetch, without surrounding network catch/finally. A rejected fetch skips flag reset.

Recommendation: preserve entered data, reset flags in finally and show a retryable error. Do not blindly retry a possibly saved funding deposit.

### R5: Medium - order details can change while a payment link is being created

Evidence: src/components/checkout-form.tsx disables submission but leaves name/contact/game fields editable during the pending request. Its payload was already captured at submit.

Impact: on a slow connection, visible edited player details can differ from those stored on the newly returned payment link. Server-side immutable snapshots protect the original order, but the buyer presentation is confusing.

Recommendation: freeze delivery/contact/package inputs until the request completes, or clearly associate the returned bill with an immutable visible summary.

### R6: Medium - operator changes lack a persistent audit trail

Evidence: audit_logs exists, but current product/order/staff write paths do not write operator action records. Code search found no application audit-log writer.

Recommendation: record actor, action, target, timestamp and safe before/after values for sensitive edits. Exclude passwords, API keys and unnecessary personal data. This is an additional capability requiring approval.

### R7: Medium - trust/policy content and security defence in depth

No dedicated privacy/refund/terms pages were found in the current route tree/navigation. Obtain the owner's actual policy/business content rather than inventing it. Some admin mutation handlers lack the explicit same-origin check used by the exchange-rate endpoint; SameSite=Lax cookies still provide an existing cross-site protection layer. Apply consistent origin validation as defence in depth. A strict CSP needs a tested Next.js-compatible nonce strategy. Previously disclosed credentials remain unchanged at the owner's explicit earlier decision; that residual risk is not resolved by this audit.

### R8: Low - maintenance and performance

- Production npm audit reports zero vulnerabilities. Development tooling reports five high-severity dependency entries in one ESLint/fast-glob/micromatch/braces chain. Do not use audit --force to downgrade Next tooling. Advisory: https://github.com/advisories/GHSA-vfj7-8cjw-p6xm.
- Supabase performance advisor reports three unindexed foreign keys: funding allocation batch, order product and order variation. Add indexes with normal migration/verification before material traffic growth. Unused-index notices are not grounds to delete recovery/ranking indexes from a newly launched store.
- The remaining Supabase security warning is pg_net installed in public. Moving a managed scheduling/network extension needs a controlled maintenance plan so the five workers are not broken. Reference: https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public.
- Smaller admin field heights/table scrolling and public About copy can be made more consistent. The Staff screen has a disabled entry duplicating the owner email; it was not deleted or enabled.

- No published, enabled variation was below its stored supplier MYR cost at the check. Live price changes can still change margins later; this is not a guarantee.
- No real paid customer order exists yet; the earlier successful launch test remains separately marked.
- Full isolated regression suite passes: checkout validation, private projection, fee totals, supplier parsing, reservations/availability, callbacks, staff permissions, recovery/idempotency, custom packages, rankings, receipts, exchange rate and funding allocation.

## Remaining verification gaps

### Additional confirmed input/editor gaps

- **Medium: manual select-field choices cannot be edited.** The product customer-field editor offers Type=Select, but no control edits field.options (src/components/admin-product-manager.tsx around line643). Imported choices are retained, but a newly created select can contain no choices and prevent checkout. Add a simple choices editor and reject publishing required selects with empty options.
- **Medium: phone validation checks characters, not a real digit count.** src/lib/validation.ts accepts eight plus signs or spaces because length and allowed-character checks do not require phone digits. Require a bounded normalized digit count and an appropriate phone input mode; do not claim that formatting validation proves WhatsApp registration.

No new live paid custom-package delivery, refund transaction, WhatsApp integration or Bahasa Malaysia release was tested. Those are not represented as complete. Public leaderboard empty-state/rendering and unit aggregation tests do not replace a future consented real-data leaderboard test. This audit does not prove concurrency under production load, provider uptime or email delivery to every mailbox.
